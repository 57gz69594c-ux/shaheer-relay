REQUIREMENT 1: SEE THE FUTURE — MEMPOOL MONITORING
================================================================

Competing MEV bots do not wait for a block to be mined to learn that a
price changed. They watch the MEMPOOL — the pool of pending unconfirmed
transactions. When a Chainlink oracle submits a price update transaction,
it sits in the mempool for 1–12 seconds before a block builder includes
it. During those seconds, MEV bots:

1. See the pending oracle update in the mempool
2. Simulate what the blockchain state will look like AFTER that update
3. Identify every position that will become liquidatable
4. Build their liquidation transaction
5. Bundle it with the oracle update via Flashbots
6. Both transactions are mined together in the same block

The liquidation opportunity NEVER EXISTS publicly. It is created and
captured in the same block. By the time our engine polls the next oracle
price, it's already done.

WHAT WE NEED:

- Mempool subscription via WebSocket to a node that exposes pending
  transactions (Geth --txpool, Erigon, or a service like Bloxroute,
  Chainbound Fiber, or Flashbots Protect RPC).

- Pending transaction decoder that identifies oracle price updates by
  contract address and function selector. Chainlink aggregators call
  transmit() or submit(). Morpho oracle calls are identifiable by their
  target contract. The engine must recognize these.

- Speculative state simulation: when a pending oracle update is detected,
  fork the current blockchain state, apply the pending transaction, then
  re-evaluate all positions against the POST-UPDATE state. This reveals
  which positions WILL become liquidatable once the oracle update is mined.

- Flashbots bundle construction: package our liquidation transaction
  together with the oracle update into a Flashbots bundle. Submit to
  block builders (Flashbots, MEV-Share, Titan, rsync). The builder mines
  both atomically in the same block. Our liquidation executes in the same
  block the opportunity is created — before anyone else even knows.

- For L2 chains (Arbitrum, Base, Optimism, Scroll): L2s don't have a
  public mempool in the same way. Instead, submit directly to the
  sequencer's private endpoint. The sequencer processes transactions
  strictly in arrival order. First to reach the sequencer wins. Minimize
  network hops between our VPS and the sequencer.

This is the single most important capability. Without it, we are always
reacting to the past while competitors are acting on the future.

REQUIREMENT 2: 500x SPEED IMPROVEMENT
================================================================

CURRENT MEASURED SPEED (from v5.5.0 logs):

  Step 1 — Oracle detection:        5,000–9,000 ms (polling via RPC)
  Step 2 — Position evaluation:     1,000–2,000 ms
  Step 3 — Swap quote (HTTP API):   1,000–10,000+ ms (timeouts common)
  Step 4 — Transaction build:       1,000–2,000 ms
  Step 5 — EVM simulation:          1,000–2,000 ms
  Step 6 — Mempool submission:      1,000–2,000 ms
  TOTAL:                            10,000–25,000 ms

TARGET SPEED (500x improvement):

  Step 1 — Oracle detection:        0 ms (mempool monitoring, see above)
  Step 2 — Position evaluation:     < 5 ms (pre-indexed position table)
  Step 3 — Swap route:              < 10 ms (pre-computed, no API call)
  Step 4 — Transaction build:       < 5 ms (template with variable fill)
  Step 5 — EVM simulation:          < 20 ms (local node fork)
  Step 6 — Flashbots submission:    < 10 ms (direct to block builder)
  TOTAL:                            < 50 ms

  Current: 10,000–25,000 ms
  Target:  < 50 ms
  Factor:  200–500x faster

HOW TO ACHIEVE EACH STEP:

Step 1 — Oracle detection at 0 ms:
  - Subscribe to mempool via WebSocket (see Requirement 1)
  - Maintain a watchlist of every Chainlink aggregator address and Morpho
    oracle address across all monitored chains
  - When a pending tx targets a watched address, immediately trigger
    speculative evaluation
  - Fallback: WebSocket subscription to new block headers + event logs
    for chains without mempool access (L2s). This gives < 500 ms instead
    of the current 5–9 second polling

Step 2 — Position evaluation at < 5 ms:
  - Keep all monitored positions in an in-memory data structure, indexed
    by oracle dependency
  - When oracle X updates, instantly look up every position that depends
    on oracle X
  - Re-calculate health factors using the new price, entirely in memory
  - No database queries, no RPC calls — pure computation on cached state

Step 3 — Swap route at < 10 ms:
  - ELIMINATE all external aggregator API calls from the critical path
  - Maintain a live routing table: for every collateral/debt token pair,
    store the best DEX pool address, current reserves/liquidity, and
    expected output
  - Update this table every block by reading pool states via multicall
  - When a liquidation is triggered, look up the pre-computed route from
    memory — no HTTP request, no waiting
  - Direct on-chain pool math: implement Uniswap V3 concentrated
    liquidity quoter, Uniswap V2 constant product, Curve StableSwap,
    PancakeSwap V3, TraderJoe, SushiSwap V3 locally
  - For each token pair, store the top 3 routes ranked by output amount
  - Aggregator APIs become a BACKGROUND process that occasionally
    validates and improves the routing table, not a blocking call

Step 4 — Transaction build at < 5 ms:
  - Pre-build transaction templates for each executor contract
  - Only fill in: borrower address, seized amount, swap route calldata,
    gas parameters
  - The template, nonce, and chain-specific parameters are pre-cached
  - ABI encoding of the variable parameters takes microseconds

Step 5 — EVM simulation at < 20 ms:
  - Run a local execution client (Reth is fastest — Rust-native, < 50 ms
    state fork and simulation)
  - Fork from the latest block state held locally
  - Apply the pending oracle update (from mempool), then simulate our
    liquidation on top
  - No network round-trip — everything is local disk/memory
  - If no local node: use a dedicated fast RPC with simulation support
    (Alchemy Transact, Tenderly, or Chainstack debug_traceCall) as
    interim, but accept 200–500 ms latency

Step 6 — Submission at < 10 ms:
  - Ethereum: Flashbots eth_sendBundle or MEV-Share. Direct HTTPS POST to
    the Flashbots relay. Include the oracle update tx hash as a
    dependency so our tx is mined in the same block.
  - Arbitrum: Direct submission to the Arbitrum sequencer endpoint
    (sequencer.arbitrum.io). Minimize hops.
  - Base/Optimism: Direct to the OP Stack sequencer.
  - Polygon: Direct to Bor validator RPC.
  - Other L2s: Fastest available RPC with sendRawTransaction.
