WHAT WAS WRONG
═══════════════════════════════════════

ROOT CAUSE #1: Wine Python IPC Bug (WinError 10038)
The MT5 REST API server used Python's select.select() on pipe file descriptors. Wine Python does NOT support select() on pipes — only sockets. This caused the worker subprocess to crash immediately after every container restart.

ROOT CAUSE #2: Worker Subprocess Startup Deadlock
The worker had a 10-second blocking sleep before reading stdin. The server only waited 3 seconds then sent commands that went unanswered. Result: server killed the worker for timeout, restarted it, same loop forever.

ROOT CAUSE #3: MT5 Terminal Not Logging In
After server reboot, the terminal process was running but never authenticated to the broker. The worker's mt5.initialize() call hung indefinitely.

ROOT CAUSE #4: Server Reboots (External — DigitalOcean)
3 reboots on Aug 26 (03:27, 04:07, 05:25 UTC). Kernel logs show "Power Button" ACPI event — DigitalOcean hypervisor maintenance, not caused by us.

═══════════════════════════════════════
WHY 16 CORES + 35GB RAM DIDN'T HELP
═══════════════════════════════════════

CPU was at 7%, RAM at 8%, zero swap, zero I/O wait. The bottleneck was a SOFTWARE BUG in the Wine Python IPC layer that caused a crash loop after every container restart. More cores and RAM cannot fix a compatibility bug.

WHAT WAS FIXED
═══════════════════════════════════════

1. MT5 REST Server v4b — replaced select.select() with thread-based readline timeout
2. MT5 Worker v3 — immediate stdin reading, lazy MT5 init, login credentials from env
3. MT5 Terminal restarted with explicit login parameters
4. Trading engine restarted — Inverse mode: OFF confirmed
5. SSH hardening: fail2ban active, 4 IPs banned (1773 brute force attempts blocked)
6. Watchdog timer: systemd timer every 2 min — detects STALLS not just dead processes
7. System health monitor: instant status via /usr/local/bin/system-health
