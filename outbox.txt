## 3. CONFLICTS / RISKS

| Risk | Severity | Mitigation |
|------|----------|------------|
| **RAM contention** — R1 zombie Claude sessions regularly consume 3-5 GB | HIGH | Trading services must be memory-efficient. Budget: 4-6 GB for trading platform max. Monitor with alerts. |
| **Shared CPU** — 8 vCPUs are shared (not dedicated) | MEDIUM | Avoid sustained CPU-intensive tasks during market hours. Run heavy backtests during off-peak. |
| **No GPU** — ML training limited to CPU | MEDIUM | Use lightweight models (XGBoost, LightGBM, logistic regression). No deep learning training — inference only for small models. |
| **Port conflicts** — 3456, 3457 already taken | LOW | Use 5xxx range for trading services (e.g., 5432 PostgreSQL, 5555 trading API). |
| **Disk space during backtests** — 5-10 years of tick data can be 50-100 GB | MEDIUM | Use 1-minute candles (much smaller), compress with Parquet. Budget: 50 GB max for all trading data. |
| **Docker overhead** — containerized DB adds memory overhead | LOW | PostgreSQL in Docker typically adds ~50-100 MB overhead. Acceptable. |
| **Caddy/Nginx conflict** — both installed | LOW | Caddy is active. Don't touch Nginx. Add trading routes to Caddy if needed. |
| **R1 rabbit-agent cron** — spawns processes every 10 min | LOW | Do not interfere. Trading processes must coexist. |

## 5. TECHNOLOGY STACK

| Layer | Technology | Why |
|-------|-----------|-----|
| **Language** | Python 3.12 | Already installed. Richest ecosystem for quant finance (pandas, numpy, scipy, sklearn, xgboost, etc.). |
| **Database** | PostgreSQL 16 + TimescaleDB | Purpose-built for time-series. Hypertables auto-partition candle data. Compression reduces storage 10-20x. Runs in Docker to avoid conflicting with existing services. |
| **Cache** | Redis 7 (Docker) | Fast key-value store for live market state, feature cache, rate limiting. Small memory footprint (~100 MB). |
| **Data Format** | Parquet (archival) + PostgreSQL (live) | Parquet for bulk historical data import/export. PostgreSQL for operational queries. |
| **ML Framework** | scikit-learn, XGBoost, LightGBM | CPU-efficient gradient boosting. No GPU needed. Proven in quant finance. PyTorch available for small neural nets if needed. |
| **Feature Engine** | pandas + ta (technical analysis library) | `ta` library provides 100+ indicators out of the box. pandas for time-series manipulation. |
| **Market Data** | yfinance (free), FRED API (free), MetaTrader5 (broker) | yfinance: 5-10 years of daily/hourly XAU/USD. FRED: macro data (yields, CPI, etc.). MT5: live tick data during forward test. |
| **News** | NewsAPI.org (free tier) or GDELT | Headline sentiment analysis. Free tier sufficient for research. |
| **Scheduling** | APScheduler or systemd timers | Run data ingestion, feature calculation, model inference on schedule. |
| **Containerization** | Docker (already installed) | Isolate PostgreSQL and Redis. Don't pollute the host system. |
| **Secrets** | python-dotenv + `/root/.trading-secrets/` (chmod 600) | `.env` file outside git repo. Never committed. Never logged. |
| **Query Interface** | CLI scripts callable by Claude Code | `trading-briefing`, `trading-status`, etc. Claude executes these and reads output. |
| **Monitoring** | systemd journal + health-check script | Lightweight. No need for Prometheus/Grafana on this server. |

## 7. MODEL ARCHITECTURE

### Layer 1: Feature Engine (Quantitative)
Pure computation. No judgment. Calculates 200-300 features from raw market data across multiple timeframes. Every feature has a strict point-in-time guarantee.

### Layer 2: Specialist Agents (Analytical)
Each specialist receives relevant features and produces a structured assessment:

| # | Specialist | Input | Output |
|---|-----------|-------|--------|
| 1 | Technical | Price action, indicators | Trend direction, strength, S/R levels |
| 2 | Momentum | Returns, ROC, RSI | Momentum score, divergences |
| 3 | Mean-Reversion | Bollinger, z-scores | Overextension score, reversion probability |
| 4 | Breakout | Range, volatility, volume | Breakout probability, direction |
| 5 | Volatility | ATR, realized vol, regime | Regime classification, expansion/contraction |
| 6 | Macro | Yields, DXY, rates | Macro environment score, bias |
| 7 | Cross-Asset | Correlations, relative moves | Confirmation/divergence signals |
| 8 | News | Headlines, sentiment | Event risk, surprise factor |
| 9 | Regime Classifier | Multi-feature ensemble | Current market regime label |
| 10 | Statistical Pattern | Historical analogues | Pattern match confidence |
| 11 | Contrarian | Consensus of other agents | Counter-argument, risk flags |
| 12 | Risk/Portfolio | Position, drawdown, exposure | Position sizing, risk limits |

Most specialists are **algorithmic** (fast, deterministic). A few high-level ones (News, Contrarian) can use **Claude API calls** when budget allows.

### Layer 3: Claude Reasoning (Strategic)
Claude receives a structured evidence packet from all specialists:
```json
{
  "timestamp": "2026-08-20T14:00:00Z",
  "market_regime": "trending_up",
  "technical_score": 0.72,
  "momentum_score": 0.65,
  "mean_reversion_score": -0.3,
  "breakout_probability": 0.45,
  "volatility_regime": "expanding",
  "macro_bias": "gold_bullish",
  "cross_asset_confirmation": true,
  "news_risk": "low",
  "contrarian_flags": ["RSI overbought on daily"],
  "ml_ensemble_probability": 0.68,
  "historical_analogues": [{"date": "2024-03-15", "similarity": 0.82, "outcome": "+1.2%"}],
  "supporting_evidence": ["Strong uptrend", "DXY weakening", "Real yields falling"],
  "contradictory_evidence": ["RSI overbought", "Near resistance at 2450"]
}
```

Claude then produces a structured decision (not a chat response):
```json
{
  "decision": "LONG",
  "confidence": 0.65,
  "horizon": "4h",
  "thesis": "Gold trending up with macro tailwinds, DXY weakness. RSI overbought is a caution but not a reversal signal in trending regime.",
  "invalidation": "Break below 2420",
  "position_size": "standard"
}
```

### Layer 4: Strategy Tournament
Multiple strategies compete. Each produces its own decision independently. Performance is tracked per-strategy, per-regime.

## 8. HISTORICAL RESEARCH DESIGN

### The Examination Protocol

```
FOR each historical timestamp T in the dataset:

  1. FREEZE the clock at T
  2. Gather ONLY data available at or before T:
     - Candles up to T (not T+1)
     - Features computed from data ≤ T
     - Macro releases published before T
     - News headlines timestamped before T
  3. Feed to models/specialists/Claude
  4. Generate prediction P(T)
  5. FREEZE prediction P(T) — write to database
  6. Advance clock to T + horizon
  7. Observe actual market movement
  8. Score prediction accuracy
  9. Record outcome alongside original prediction
  10. NEVER modify P(T) after the fact

VIOLATION DETECTION:
  - Every feature has a computation timestamp
  - Every data point has an availability timestamp
  - Audit log flags any access to data with timestamp > T
  - Economic data uses FIRST RELEASE values, not revised values
```

### Walk-Forward Windows (example for 10-year dataset)

```
Period 1: TRAIN [2016-2018] → VALIDATE [2019-H1] → TEST [2019-H2]
Period 2: TRAIN [2016-2019] → VALIDATE [2020-H1] → TEST [2020-H2]
Period 3: TRAIN [2016-2020] → VALIDATE [2021-H1] → TEST [2021-H2]
Period 4: TRAIN [2016-2021] → VALIDATE [2022-H1] → TEST [2022-H2]
Period 5: TRAIN [2016-2022] → VALIDATE [2023-H1] → TEST [2023-H2]
Period 6: TRAIN [2016-2023] → VALIDATE [2024-H1] → TEST [2024-H2]
Period 7: TRAIN [2016-2024] → VALIDATE [2025-H1] → TEST [2025-H2]
Period 8: TRAIN [2016-2025] → VALIDATE [2026-H1] → FORWARD TEST [live]

FINAL HOLDOUT: 2025-H2 through 2026 — NEVER optimized on.
```

## 9. ANTI-OVERFITTING DESIGN

### The Seven Deadly Sins of Backtesting

| Sin | How We Prevent It |
|-----|-------------------|
| **Look-ahead bias** | Strict point-in-time data access. Feature engine enforces timestamp boundaries. Audit trail flags violations. |
| **Data leakage** | Train/validate/test split enforced programmatically. No feature uses future candle data. Features computed from rolling windows only. |
| **Survivorship bias** | Not critical for XAU/USD (gold doesn't get delisted), but we track instrument changes and contract rollovers. |
| **Overfitting to noise** | Require strategies to pass multiple independent test periods. Performance must be consistent across regimes. |
| **Unrealistic execution** | All backtests include: spread (configurable, default 3 pips for XAU), slippage (1-2 pips), commission, and execution delay (1 candle minimum). |
| **Parameter mining** | Track number of parameters per strategy. Penalize complexity. Require that Sharpe ratio exceeds threshold AFTER adjusting for degrees of freedom. |
| **Selection bias** | The strategy tournament includes random and simple baselines. Any "smart" strategy must beat buy-and-hold AND random entry with trailing stop. |

### Automatic Overfitting Detection
```
IF in_sample_sharpe / out_of_sample_sharpe > 2.0:
    FLAG: "Likely overfit — in-sample performance degrades 50%+ out of sample"

IF parameter_count > 10 AND sample_size < 500:
    FLAG: "Too many parameters for available data"

IF strategy works in only 1 of 4 market regimes:
    FLAG: "Regime-specific — not robust"

IF win_rate > 80%:
    FLAG: "Suspiciously high — check for look-ahead bias"
```

## 10. STRATEGY TOURNAMENT DESIGN

### Tournament Structure
```
TIER 1 — BASELINES (must beat these to be "interesting")
  ├── Random entry + trailing stop
  ├── Buy-and-hold gold
  ├── Simple 50/200 EMA crossover
  └── Monthly rebalance (50% gold / 50% cash)

TIER 2 — SIMPLE SYSTEMATIC
  ├── Momentum (12-month return > 0 → long)
  ├── Mean reversion (RSI < 30 → long, > 70 → short)
  ├── Breakout (N-day high/low break)
  ├── Volatility expansion (ATR breakout)
  └── Trend following (ADX + EMA direction)

TIER 3 — MULTI-FACTOR
  ├── Technical ensemble (vote of 5+ indicators)
  ├── Macro model (yields + DXY + rate expectations)
  ├── Cross-asset model (gold vs correlated markets)
  └── ML ensemble (XGBoost on 50+ features)

TIER 4 — AI-AUGMENTED
  ├── Claude reasoning on structured evidence
  ├── Claude + ML ensemble
  ├── Claude + specialist agent votes
  └── Full system (all layers combined)

TIER 5 — EVOLVED
  ├── Mutated variants of winning strategies
  ├── Parameter-optimized versions
  └── Regime-conditional combinations
```

### Ranking Criteria (not just profit)
1. **Risk-adjusted return** (Sortino ratio — penalizes downside only)
2. **Maximum drawdown** (survival matters more than peak profit)
3. **Consistency** (performance across all walk-forward periods)
4. **Robustness** (in-sample vs out-of-sample degradation)
5. **Simplicity** (fewer parameters preferred, all else equal)
6. **Regime breadth** (works in trending AND ranging markets)

## 11. SHADOW PORTFOLIO DESIGN

### Starting Capital: $100 per portfolio

Each shadow portfolio tracks a virtual $100 account. No real money. All execute against the same market data stream.

### Portfolio Categories

```
PRIMARY (10 portfolios)
  ├── Full system (all agents + Claude + ML)
  ├── High-confidence only (>70% confidence trades)
  ├── Claude reasoning only (no ML)
  ├── ML only (no Claude)
  ├── Technical only
  ├── Macro only
  ├── Momentum only
  ├── Mean reversion only
  ├── Breakout only
  └── Random baseline

PARAMETER VARIANTS (20+ portfolios)
  ├── Tight stops (0.5x ATR)
  ├── Wide stops (2x ATR)
  ├── Trailing stops
  ├── Fixed target (1:2 risk/reward)
  ├── Time-based exit (4h, 1D, 1W)
  ├── Half position size
  ├── Double position size
  ├── Delayed entry (+5 min, +15 min, +1h)
  └── Regime-filtered (only trade in trending markets)

ABLATION (10+ portfolios)
  ├── System minus news agent
  ├── System minus macro agent
  ├── System minus volatility filter
  ├── System minus cross-asset
  └── System minus contrarian
```

### Tracking Per Portfolio
- Running balance
- Open positions
- Trade history
- Cumulative P/L curve
- Maximum drawdown
- Win rate
- Sharpe/Sortino
- Comparison vs buy-and-hold benchmark

## 12. ONE-WEEK FORWARD TEST DESIGN

### Prerequisites (must be completed first)
1. Historical backtest complete with positive out-of-sample results
2. Strategy selected from tournament
3. MT5 DEMO account connected
4. Data ingestion pipeline running live
5. Feature engine running in real-time
6. Decision journal system operational

### 7-Day Protocol

```
DAY 0 (Setup):
  - Connect MT5 DEMO account
  - Verify live data feed
  - Start all shadow portfolios at $100
  - Log starting market conditions

DAYS 1-7 (Continuous):
  Every decision interval (e.g., hourly or 4-hourly):
    1. Ingest latest market data
    2. Calculate features (point-in-time)
    3. Run all specialist agents
    4. Generate prediction — FREEZE before market moves
    5. If signal → place DEMO trade via MT5
    6. Update all shadow portfolios
    7. Score previous predictions against actual outcomes
    8. Log everything to decision journal

  Every 24 hours:
    1. Generate daily summary
    2. Compare shadow portfolio rankings
    3. Evaluate confidence calibration
    4. Detect any system errors/anomalies
    5. Email summary to Shaheer (via M365)

DAY 7 (Report):
  Generate comprehensive report:
    - Total predictions made
    - Accuracy by confidence band
    - P/L of each shadow portfolio
    - Best/worst trades with analysis
    - Comparison to baselines
    - System uptime and errors
    - Confidence calibration chart
    - Regime analysis
    - Honest assessment: did the system add value?
```

### Critical Rule
NO prediction may be modified after it is made. The database enforces immutability on prediction records (INSERT only, no UPDATE/DELETE on predictions table).

1. Connects to PostgreSQL
2. Queries relevant tables
3. Formats output as concise, speakable text
4. Prints to stdout (Claude reads it)

## 16. OPEN QUESTIONS (Requiring User Input)

### Q1: MetaTrader 5 Connectivity (CRITICAL)
The MT5 Python package (`MetaTrader5`) only works on Windows. This Linux server cannot run it natively.

**Options:**
- **(A)** Install MT5 via Wine in Docker — experimental, may be unreliable
- **(B)** Use a third-party bridge like `mt5linux` or `dwx-zeromq-connector` — requires MT5 running somewhere (your iPhone app or a Windows VPS)
- **(C)** Skip MT5 for now, use yfinance for market data, do paper trading purely in our database (no actual DEMO orders placed in MT5)
- **(D)** Get a small Windows VPS ($5-10/month) to run MT5 headless, bridge to this server

**Recommendation:** Start with **(C)** — pure database paper trading. Add MT5 bridge later when the system proves it has an edge.

### Q2: Dominion Markets MT5 DEMO Credentials
When we're ready for the forward test, I'll need the MT5 DEMO account credentials (login, password, server). These will be stored in `/root/.trading-secrets/.env` with strict permissions. **Not needed now — only when Milestone 10 begins.**

### Q3: Claude API Budget for Trading
The specialist agents and Claude reasoning layer will make Claude API calls. Each trading decision might use 1-2 API calls (~$0.01-0.05 each). During backtesting over 10 years of hourly data, this could mean thousands of API calls.

**Options:**
- **(A)** Use Claude API only for forward testing (cheapest — backtest uses ML only)
- **(B)** Use Claude API for a sample of historical decisions (100-200 calls for calibration)
- **(C)** Use Claude API for all decisions (expensive for backtesting, most thorough)

**Recommendation:** **(B)** — sample-based historical calibration, then full Claude integration for forward test.

### Q4: News Data Source
Free news APIs have limitations. For historical news analysis:
- **GDELT** — free, massive, but noisy
- **NewsAPI.org** — free tier: 100 requests/day, 1 month history
- **Alpha Vantage News** — free tier available

**Recommendation:** Start with GDELT for historical, NewsAPI for live. Upgrade if needed.

### Q5: FRED API Key
FRED (Federal Reserve Economic Data) is free but requires an API key.
**Action:** Register at https://fred.stlouisfed.org/docs/api/api_key.html (free, instant). Send the key via Claude Relay when ready.

With R1 sessions and other services, RAM is occasionally tight. How much RAM should the trading platform be allowed to use?

**Recommendation:** Cap at 4 GB (PostgreSQL 1.5 GB, Redis 500 MB, Python workers 2 GB). This leaves 8+ GB for existing services.

## HONEST ASSESSMENT

### What Will Work Well
- **Historical backtesting** — we have the compute, the data is free, the methodology is sound
- **Feature engine** — 200+ indicators on CPU is trivial, pandas handles this easily
- **Strategy tournament** — excellent way to prevent self-deception
- **Shadow portfolios** — cheap to run, highly informative
- **Claude query interface** — natural fit with existing Even G2 workflow
- **Anti-overfitting framework** — the most important part of the entire system

### What Will Be Challenging
- **MT5 on Linux** — real technical challenge, may need Windows VPS
- **No GPU** — limits ML to gradient boosting (which is actually fine — often beats neural nets on tabular financial data)
- **Shared server** — RAM contention with R1 sessions is real
- **News analysis** — free sources are noisy, may not add much value
- **Claude API costs** — could add up during intensive backtesting

### What I Won't Promise
- **Profitability** — no trading system should promise this. The entire design is built around discovering whether an edge exists, not assuming one does.
- **That AI beats simple strategies** — the tournament will tell us. If EMA crossover wins, we report that honestly.
- **Real-time tick-level trading** — this server's latency to exchanges makes sub-second trading impossible. We're targeting 1-hour to daily timeframes.
