A. FEATURE ENGINE ARCHITECTURE
───────────────────────────────
Wide-table Parquet approach per timeframe.

Design decision: feature values stored as Parquet files
(one per timeframe/instrument/version), NOT in the database.
Feature definitions stored as JSON for versioning.

Rationale:
  - Daily: 294 features × 6,515 rows = ~1.9M cells → 15 MB Parquet
  - Hourly: 128 features × 11,462 rows = ~1.5M cells → 12 MB Parquet
  - ML extraction: single file read, zero JOINs
  - Alternative (EAV tall-table) rejected: 200× more rows, impractical

Feature definitions include: feature_id, name, version, category,
description, formula, required_inputs, lookback, timeframe,
point_in_time_safe, provider_dependencies, instrument, is_proxy.

422 feature definitions exported to feature_definitions.json.
Feature manifest with checksum for reproducibility.

C. GC FUTURES ANOMALY INVESTIGATION
────────────────────────────────────
FINDING: 1 row where high < low in GC_FUTURES daily data.

Investigation:
  This is a yfinance provider artifact, NOT a real market event.
  COMEX gold futures never trade with high < low.
  Caused by continuous-contract adjustment rounding.

Resolution:
  - Raw candle preserved in database (never deleted)
  - Candle classified as INVALID_OHLC
  - Excluded from feature computation via get_clean_candles()
  - 6,515 valid candles used (out of 6,516 total)

Rollover awareness:
  GC futures is a continuous futures series. Exact contract-chain
  data is unavailable from yfinance. Roll dates cannot be
  precisely identified without contract specifications.

  LIMITATION DOCUMENTED: Features derived from GC_FUTURES may
  contain rollover artifacts. All gc_ prefixed features carry
  this provenance. When true XAU/USD spot data arrives from
  Dominion/MT5, features will be recalculated as xauusd_ prefix.

G. POINT-IN-TIME SAFETY
────────────────────────
How leakage is prevented:

1. DAILY CROSS-ASSET: T-1 lag applied via merge_asof(backward).
   For GC_FUTURES date T, all cross-asset data comes from T-1.
   Different trading calendars handled correctly (merge_asof
   finds most recent available observation, never forward).

2. HOURLY CROSS-ASSET: merge_asof(direction='backward').
   For each primary timestamp, finds most recent context
   observation with event_time <= primary event_time.

3. ROLLING WINDOWS: All use min_periods=window_size.
   No centered windows. No expanding windows that use future.
   Pandas rolling with default closed='right'.

4. TARGETS: Physically separate from features.
   Stored in data/targets/, never in data/features/.
   feature_snapshot() API never returns target values.
   shift(-horizon) used → trailing NaN proves forward-looking.

5. NORMALIZATION: Rolling/expanding statistics only.
   No global fit_transform across entire history.
   Z-scores use rolling mean/std, not dataset-wide.

6. NO_TIME_TRAVEL TESTS: 15 dedicated leakage tests.
   Intentionally verify each feature type uses past only.


H. CROSS-ASSET ALIGNMENT
─────────────────────────
DAILY ALIGNMENT:
  Method: shift(lag=1) on context index → merge_asof(backward)
  Rule: for primary date T, use context value from T-1
  Handles different calendars: FX trades different days than equities
  Missing values: NaN (ALIGNMENT_GAP), not forward-filled

HOURLY ALIGNMENT:
  Method: pd.merge_asof(direction='backward')
  Rule: for each primary timestamp, find most recent context
  observation at or before that time
  No forward fill. Gaps remain as NaN.

Alignment gaps detected:
  EURUSD D1: 12.4% missing (FX calendar vs futures calendar)
  GLD_ETF D1: 16.2% missing (ETF started 2004, GC from 2000)
  All others: <1% missing
